## S1 — Defects

### 1. `context-budget.sh` reports PASS for a root with no `.claude` directory

I ran `./scripts/context-budget.sh ~/projects/tegonal/globe-website/frontend`. The script returned
zero always-loaded files, `"claude_md": {"status": "MISSING"}`, and `"status": "PASS"`.

That directory exists. `.claude` inside it does not. The script therefore passed a project that has no
Claude Code configuration at all.

A scan over zero files is a failed run. `.claude/rules/writing-rules.md` states this rule for
`ste-check.ts` and `dupe-check.ts`, which exit 2 when they find no file. `context-budget.sh` breaks the
same rule, and the maintenance flow trusts its verdict.

**Fix:** validate the root first. Exit 2 when `.claude/rules/` is absent, and exit 2 when the scan
finds no rule file and no `CLAUDE.md`.

### 2. `SKILL.md` is 561 lines and the limit is 500

The skill authoring page states the limit twice: "Keep SKILL.md body under 500 lines for optimal
performance." Finding 11 of the previous review measured 590 lines and asked for a size check in
`gen-inventory.sh`. The check was never added, so the file drifts without a signal.

`## Invocation Instructions` is 204 lines. It is a step list that a reader consults once per
invocation. Move it to `references/invocation.md` and the file drops to about 360 lines.

**Fix:** extract the section, then add a line count check to `scripts/gen-inventory.sh --check`.

## S2 — Facts in the documentation that the skill does not carry

### 3. Every subagent pays the always-loaded set again

The subagents page lists what loads in a fresh subagent context: "CLAUDE.md files: every level of the
CLAUDE.md hierarchy the main conversation loads, including `~/.claude/CLAUDE.md`, project rules,
`CLAUDE.local.md`, and managed policy files."

Project rules are in that list. A target project therefore pays 84 KB in the main session and 84 KB
again in each subagent. The three deployed agents run for narrow tasks. None of them sets
`omitClaudeMd`.

The page names the escape: "A subagent whose definition sets `omitClaudeMd` loads only the managed
policy files, or none at all."

**Fix:** decide per agent, and name the cost each time. `code-reviewer` judges code against the
deployed conventions, so it must keep the load. `mechanical-replacer` cites no rule in its 89-line
body and makes no judgment call, so it is the candidate. Its report then loses the language rule,
because that rule reaches a subagent through the same hierarchy.

### 4. Skill content survives compaction only in part

The skills page states the lifecycle: the rendered `SKILL.md` enters the conversation as one message
and stays across later turns. After auto-compaction, Claude Code re-attaches "the most recent
invocation of each skill after the summary, keeping the first 5,000 tokens of each".

`SKILL.md` at 561 lines is above 5,000 tokens. A long `/webstack maintenance` run compacts, and the
tail of the file is then absent. The 13 maintenance steps live in `references/maintenance.md`, so they
survive. The invocation steps in `SKILL.md` do not.

**Fix:** finding 2 already moves them. Order the remaining sections so the rules that must hold all
session stand first.

### 5. `context: fork` runs a skill in its own subagent

The skills page documents the field: "Add `context: fork` to your frontmatter when you want a skill to
run in isolation." The forked subagent runs in the background, and `background: false` makes the turn
wait.

`/webstack maintenance` is a 13-step batch job that reports a result. It fits the pattern.
`/webstack init` and `/webstack update` do not, because they ask the user questions.

**Three constraints.** The fork does not see the conversation history, so a forked maintenance run
needs the project path in its own prompt. The page states that Claude Code starts a subagent "of the
type set in the `agent` field", so the skill must name one. A separate skill also changes the
invocation from `/webstack maintenance` to `/webstack-maintenance`, which breaks the current
`argument-hint: [init|update|maintenance]` contract.

**Fix:** consider a separate `webstack-maintenance` skill with `context: fork` and an `agent` field.
Do not add the field to the current skill, because all three subcommands share it.

### 6. The script paths are hardcoded, and `allowed-tools` covers one turn

The skills page documents the pattern with `${CLAUDE_SKILL_DIR}`:

```yaml
allowed-tools: Bash(${CLAUDE_SKILL_DIR}/scripts/render.sh *)
```

Claude Code substitutes the variable in the frontmatter and in the body. The rule then matches the
command the body tells Claude to run, and the script runs without a prompt.

`SKILL.md` writes every script call with a hardcoded install path, for example
`~/.claude/skills/webstack/scripts/preflight.sh` at line 93. The init flow calls `preflight.sh`,
`bootstrap-claude-md.sh` and `sync.sh` that way. Each call prompts today.

**The two halves of this finding differ in value.**

The path half stands alone. A hardcoded `~/.claude/skills/webstack/` breaks a project-level install and
any install under a different folder name. `${CLAUDE_SKILL_DIR}` expands to the install directory, so
it works in both cases. I did not verify what it yields for a symlinked install, which is the method
this repository documents.

The permission half buys one turn. The grant clears when the user sends the next message. `init` and
`update` ask the user questions, so every script call after the first answer prompts as it does today.
The gain is `preflight.sh` and the first `sync.sh` call.

**Fix:** replace each `~/.claude/skills/webstack/` prefix in the body with `${CLAUDE_SKILL_DIR}/`. Add
`allowed-tools: Bash(${CLAUDE_SKILL_DIR}/scripts/* *)` to the frontmatter for the first-turn gain.

### 7. The `InstructionsLoaded` hook event measures what the budget script estimates

The hooks reference documents the event: "Fires when a `CLAUDE.md` or `.claude/rules/*.md` file is
loaded into context." It fires at session start for eager files, and again for a lazy load. The matcher
runs against `load_reason`, with the values `session_start`, `path_glob_match` and `nested_traversal`.

`context-budget.sh` counts bytes on disk. It cannot tell which path-scoped rule a real session loads.
This event answers that question per session.

**Fix:** add an optional hook that appends each load to a log. Use the log to find scoped rules that
never fire and always-loaded rules that no session needs.

### 8. Project rules follow `--setting-sources`

The memory page states the change: "Project rules are skipped if you exclude `project` from
`--setting-sources`. Before v2.1.211, rules that load on demand, including path-scoped rules and rules
in nested `.claude/rules/` directories, loaded even when `project` was excluded."

A CI run or an SDK run that sets `--setting-sources` without `project` gets none of the deployed rules.
`core/claude-config/claude-settings.md` does not state this.

**Fix:** add the fact to `claude-settings.md`.

### 9. The symlink install is documented, and one folder name is reserved

The skills page confirms the install method this repository uses: a skill entry in the personal
location can be a symlink to a directory elsewhere on disk. Claude Code reads `SKILL.md` from the
target.

The same list names a reserved folder: do not name a skill folder `synced`, in any capitalization.
Claude Code uses `~/.claude/skills/synced/` for skills downloaded from claude.ai. The name `webstack`
is safe.

**Fix:** record the reserved name in `README.md` next to the install command.

## S3 — One architecture option

### 10. The skill folder can become a plugin

The plugins page documents the route: `claude plugin init my-tool` creates
`~/.claude/skills/my-tool/` with a `.claude-plugin/plugin.json` manifest. It loads as
`my-tool@skills-dir` with no marketplace and no install step. A plugin bundles agents, hooks and MCP
servers.

This skill copies agents into `.claude/agents/` and hooks into `.claude/hooks/` in each target project.
A plugin distributes both without a copy.

**The trade-off is scope, and it runs the wrong way for this skill.**

- Plugin hooks run "when the plugin is enabled", per the hooks guide scope table. `enabledPlugins`
  sets enablement per user or per project.
- A personal enablement therefore applies the agents and the hooks to every project on the machine,
  including projects that never ran `/webstack init`.
- Plugin skills are namespaced, so the command name changes.

**Recommendation:** keep the copy-based deployment. The current design gives each project an explicit
opt-in and a committed, reviewable copy. Revisit only if you want one machine-wide rule set.

## S4 — The import question

### 11. An import cannot put the operating rules first, and it saves nothing

The memory page answers both halves.

On cost: "Splitting into `@path` imports helps organization but doesn't reduce context, since imported
files load at launch." And: "Imported files are expanded and loaded into context at launch alongside
the CLAUDE.md that references them."

On order: "Rules without `paths` frontmatter are loaded at launch with the same priority as
`.claude/CLAUDE.md`." `CLAUDE.md` and each always-loaded rule file arrive as separate labeled blocks.
The order inside one file is yours. The order between the blocks is not.

So an import changes neither the byte cost nor the position. Three mechanisms remain, and this
repository already uses the strongest one.

| Mechanism | Effect | State here |
|-----------|--------|------------|
| A `UserPromptSubmit` hook | Injects the rule with every user message | In use for the language rule |
| Order inside one file | Puts the rule at the top of that block | Available |
| `paths:` on a rule | Removes the rule from the launch cost | In use for 19 of 28 core templates |

**What to do instead, for this repository's `CLAUDE.md`.** The file is 101 lines, and the content is
architecture. The memory page describes the `/doctor` trim heuristic: it "cuts content Claude can
derive from the codebase, such as directory layouts, dependency lists, and architecture overviews, and
keeps pitfalls, rationale, and conventions that differ from tool defaults."

By that rule, the sections `## Architecture`, `### Frontmatter Schema` and `### Vendor Docs` are
derivable from `manifest.json` and from the templates. Move them to a path-scoped rule under
`.claude/rules/` and keep the conventions in `CLAUDE.md`.

**Do not move `.claude/rules/*.md` into `CLAUDE.md`.** `.claude/rules/writing-rules.md` requires
`interaction.md` and `fetching.md` to mirror `core/interaction` and `core/tooling` on purpose, because
this repository does not deploy its own `core/` templates. A copy in `CLAUDE.md` makes a third site to
keep in step.

**What to do for the deployed template.** `references/bootstrap-template.md` already places
`## How you answer` first. That is correct and needs no change. Its `## Architecture` section is
project-specific and stays.
