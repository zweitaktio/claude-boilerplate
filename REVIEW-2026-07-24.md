## The through-line

Findings #2, #4 and #10 are one failure mode, not three: **SKILL.md hand-maintains inventories of files
that change** — an always-loaded list, a budget table with per-file line counts, a hooks table, and a
directory tree, covering ~50 files across `core/`, `vendor/` and `.claude/hooks/`. Every one of them has
drifted from disk since the last few commits, and each will drift again after the next. The durable fix
isn't correcting the entries; it's generating them (or dropping the ones `find` already answers). Worth
deciding that before spending edits on the individual rows.

## S1 — Blocking

### 1. Preflight checks a tool name that no longer exists

`SKILL.md:123`

```
3. Check if `mcp__plugin_context-mode_context-mode__execute` is available — if not, report
   "context-mode plugin not installed. …" and stop
```

The current tool is `mcp__plugin_context-mode_context-mode__ctx_execute`. The `__execute` name is from an
older context-mode release, so **the check cannot pass on its literal terms** — and it gates every
`/webstack init`, `/webstack update`, and `/webstack maintenance`.

Whether a given run actually halts is not something I tested. An agent may well resolve the check against
the Plugins table 19 lines above it (`SKILL.md:104`: *"Any `mcp__plugin_context-mode_*` tool available"*),
which the installed plugin satisfies. But that leaves the outcome dependent on which of two contradicting
instructions the agent weights — the failure mode is a hard stop at step 0 with a misleading "plugin not
installed" message, and it recurs on every invocation.

The same stale names are frozen into this repo's own `.claude/settings.local.json` allow list
(`…__execute`, `…__search`, `…__index`, `…__batch_execute`, `…__fetch_and_index`), which is where the
value in SKILL.md most likely came from.

**Proposed:** correct to `…__ctx_execute`. Better: check for *any* `mcp__plugin_context-mode_*` tool, as
the Plugins table at `SKILL.md:104` already specifies — that phrasing is version-proof and the two
sections currently contradict each other.

### 2. The context budget is wrong by 2.3×, and the always-loaded inventory lists the wrong files

`SKILL.md:29-37` (list), `SKILL.md:56-69` (budget table)

Measured against the actual templates:

| | SKILL.md claims | Actual |
|---|---|---|
| Always-loaded total | ~950 lines / **~23 KB** | 970 lines / **52.1 KB** |
| File count | 9 | 9 — but not the same 9 |

The set is wrong in both directions:

- **`core/process/monorepo`** is listed as always-loaded (`SKILL.md:36`) but has `paths:` frontmatter
  (`packages/**`, `apps/**`, …) — it is path-scoped. It is also 110 lines, not the ~30 the table claims.
- **`core/process/requirements-engineering`** (93 lines, `applies: Always`, `priority: high`, **no**
  `paths:`) is genuinely always-loaded and appears **nowhere** in SKILL.md — not the list, not the budget
  table, not the directory tree.
- **`core/process/code-change-gates`** (39 lines, `priority: high`, path-scoped to source files) is also
  absent from every inventory.

Per-row drift in the budget table (claimed → actual): `mcp-tools` ~145 → 69 · `engineering-discipline`
~150 → 223 · `monorepo` ~30 → 110 · `code-review` ~120 → 99 · `knowledge-base` ~120 → 93 ·
`interaction` ~25 → 45.

This matters more than a stale number: `SKILL.md:56` uses the figure as the decision rule — *"If adding new
always-loaded rules, check whether path-scoping is possible first."* The real 52.1 KB is **2.6× over the
20 KB budget `scripts/context-budget.sh` enforces** (`BUDGET_BYTES=20480`, line 51), so the gate that's
supposed to hold the line has already been silently crossed.

The byte figures are directly comparable: `context-budget.sh:61` measures whole-file size and sums it with
`jq`, which is the same thing measured here. The line count, by contrast, is within 2% of the claim — so
the "~23 KB" appears to be a stale or differently-derived figure rather than a typo, and correcting it
changes what the gate permits.

**Proposed:** regenerate the table from the templates rather than maintaining it by hand — the numbers are
`wc -l` / `wc -c` over `core/**/*.md` with no `paths:`. A hand-kept inventory of 25 files will drift again.

### 3. `find-strays.sh` reports the project wiki as strays

`scripts/find-strays.sh:161` · surfaced at `SKILL.md:596-601`

```bash
find "$RULES_DIR" -name '*.md' -type f
```

No exclusion for `rules/project/`. Run against this repo it returns 6 entries — all legitimate:

```
.claude/rules/project/pitfalls/hook-testing-inline-json-pipes.md
.claude/rules/project/pitfalls/bash-subshell-counter-loss.md
.claude/rules/{interaction,git,fetching,writing-rules}.md
```

Maintenance step 7 then tells the user these are strays to *"keep, convert into a wiki page (`wiki.sh
new`), or delete."* Two of them **are** wiki pages. This directly contradicts the guarantee stated three
times elsewhere (`SKILL.md:253`, `SKILL.md:439`, `SKILL.md:459`) that `.claude/rules/project/` is
project-owned and never touched — and the offered remedy is deletion of the project's own knowledge base.

It also has the inverse failure: it only scans `.claude/`, so the genuine root-level strays in this very
repo (`PLAN-md-rules-optimization.md`, `PROPOSAL-wiki-memory.md`) are not reported.

**Proposed:** exclude `rules/project/**` and `docs/**` from the scan; extend the scan to repo-root `*.md`
outside the known set.

## S2 — Correctness

### 4. Hooks inventory table is wrong in five ways

`SKILL.md:339-364`

- `SKILL.md:339` — *"All hooks are `.mjs` files"* — false since the TypeScript migration (`420d173`).
  Three are `.ts`, and `manifest.json:7` already includes `*.ts`.
- Wrong extensions: `completion-gate.mjs`, `rules-guard.mjs`, `wiki-discipline.mjs` are all `.ts` on disk.
- **Phantom entries** — `post-plan-review.sh`, `stop-gate.sh`, `auto-check.sh` do not exist and are not
  dispatched. The `TaskCompleted` row attributed to `post-plan-review.sh` is actually an inline `echo` in
  `settings.json`.
- **Missing entries** — `requirements-gate.mjs` (PreToolUse/`EnterPlanMode`) and `edit-review.mjs`
  (PostToolUse/`Edit|Write`) are dispatched but undocumented.
- Wrong matcher — research gate is listed as `EnterPlanMode|Task`; `settings.json` has
  `EnterPlanMode|ExitPlanMode|Task`.

Documentation-only — dispatch works. But this is the table a user reads to understand what's running.

### 5. The `.dir/path` applies operator cannot glob — one vendor template can never deploy

`scripts/evaluate-applies.sh:168-175` uses a literal `[ -d "$PROJECT_PATH/$cond" ]`. No expansion.

`vendor/dokploy-monorepo-cicd.md:3` declares:

```yaml
applies: dokploy | .github/workflows/*dokploy* | .github/workflows/*deploy*
```

Verified: with `.github/workflows/deploy-prod.yml` and `deploy-staging.yml` actually present, the
evaluator still returns `Directory .github/workflows/*deploy* not found`. Both glob branches are dead, so
the template only deploys when `dokploy` is a package dependency — which, for a deployment platform, it
generally isn't. `manifest.json:42` sets `conditional: true` on the vendor group, so this fails silently.

**Proposed:** either add glob support to the operator (and document it as a *path* test, not a *directory*
test), or change the template's condition to a real directory (`.github/workflows`).

### 6. `context-budget.sh` can't see rules in `.claude/rules/` root or `vendor/`

Its own usage text (`scripts/context-budget.sh:19-23`) scopes it to `.claude/rules/core/` and
`.claude/rules/project/`. Run against this repo it reports `"always_loaded_lines": 0` — while
`.claude/rules/{git,interaction,fetching,writing-rules}.md` were injected into this session's context in
full. Bare `.claude/rules/*.md` is the native Claude Code location and the layout this repo itself uses,
so the blind spot is not hypothetical. `vendor/` is excluded too, understating path-scoped cost.

### One new finding, found while fixing

**`migration-guard` fires on any path containing "migration".** Editing
`.claude/hooks/migration-guard.mjs` itself triggers a database-migration warning, and so would
`MIGRATION-REPORT.md` (which `kg-to-wiki.sh` generates) or a doc about migrations. The matcher is a
filename regex with no check that the file is actually a migration. Low severity — it warns, never
blocks — but it trains people to dismiss the warning, which is exactly what you don't want from a guard
on irreversible operations. Left unfixed: narrowing it needs a call on what counts as a migration in
this stack, which is a design decision rather than a repair.
